# 作战区（lab）— 设计文档

日期：2026-08-05

> **本文的可见性方案改过两次，最终回到原点。**
>
> 原设计为「dev 可见 / build 排除 / 不进 git」的内部工作区 → 2026-08-05 改为直接公开 → **2026-08-06 恢复隔离**，起因是确认了首个项目的产品尚未上市。
>
> 全过程记录在文末「决策变更记录」一节——**那一节比本文其余部分更值得读**，尤其是失误的性质那一段。

## 目标

知识库已有方法论、Prompt 库、工具地图、实战流水线和八篇案例，但全部是**事后写**的内容——要么是教学演示，要么是第三方逆向拆解。缺的是一个**边做边写**的地方：真实项目正在进行时，产物往哪放、下一步做什么。

`lab/` 补这个缺口。它不是第九个案例板块，是作战区。

## 定位

| 板块 | 回答什么 | 写作时机 |
|---|---|---|
| `method/` `prompts/` `tools/` | 该怎么做 | 事后提炼 |
| `pipelines/` | 这套工具组合怎么跑 | 事后提炼 |
| `cases/` | 别人 / 演示项目怎么做的 | 事后复盘 |
| **`lab/`** | **这个项目做到哪了、下一步做什么** | **进行中，边做边写** |

核心区别：**lab 里的文件是工作产物本身，不是对工作的记录。**

`01-proposal.md` 就是要发给客户的那份提案，写完直接用；不是「提案的总结」。这一条决定了写作风格——面向客户和自己，不面向读者。

> **由此产生的一条约束**：对客文件（提案、物料清单）不能包含指向知识库的内部链接。客户拿到的是一份独立文档，点不开 `/cases/...`。
>
> 内部推演过程与被否方案，放在项目首页的「内部决议记录」里，不混进对客文件。

## 目录结构

```
docs/lab/
├── index.md                    项目看板
└── <project-slug>/
    ├── index.md                项目首页：状态 / 待办 / 内部决议记录
    ├── 00-brief.md             客户原始需求 + 我们的解读
    ├── 01-proposal.md          提案            ← 直接发客户
    ├── 02-materials.md         物料清单        ← 向客户索要
    ├── 03-storyboard.md        分镜
    ├── 04-prompts.md           Prompt 组（按工具分开写）
    ├── 05-genlog.md            生成日志：跑了多少、废了多少、为什么废
    ├── 06-review.md            复盘
    └── assets/                 客户物料、参考图
```

### 各文件的职责边界

| 文件 | 写什么 | 不写什么 |
|---|---|---|
| `index.md` | 当前状态、下一步、卡在哪、**内部决议与被否方案** | 过程细节 |
| `00-brief.md` | 客户原话、我们的解读、已知与未知的分界 | 我们的方案 |
| `01-proposal.md` | 给客户看的完整提案，每条建议附理由 | 内部推演、内部链接 |
| `02-materials.md` | 索要清单，每项标注「缺了会怎样」 | —— |
| `03-storyboard.md` | 镜头表、时长、景别、光位 | Prompt 原文 |
| `04-prompts.md` | 可直接粘贴的 Prompt，按工具分组 | 分镜逻辑 |
| `05-genlog.md` | 每轮生成的条数、采用数、废片原因 | 成功经验（留给复盘） |
| `06-review.md` | 决策的理由、失败的尝试、如果重做 | —— |

`05-genlog.md` 是这套结构里最容易被跳过、也最有价值的一份。真实出片率只能靠当场记，事后一定记不准。

## 可见性

**不公开**，三层隔离（2026-08-06 恢复，此前曾短暂公开，经过见文末）：

| 层 | 机制 |
|---|---|
| dev 可见 | `const isDev = process.argv.includes('dev')`，nav/sidebar 条件注入 |
| build 排除 | `srcExclude: isDev ? [] : ['lab/**']` |
| git 排除 | `.gitignore` 中的 `docs/lab/` |

判断 `process.argv` 而非 `NODE_ENV`，因为 `vitepress preview` 跑的是构建产物，行为必须与 build 一致。

### 导航配置也必须隔离

第一次实现三层隔离时漏掉的一点：**`config.mts` 里的 sidebar 条目包含客户名与项目名**。页面排除了，源码里的客户名还在，且 `config.mts` 是必须进仓库的文件。

现在的做法是把作战区的 nav/sidebar 抽到 `docs/.vitepress/lab.local.json`，该文件一并 gitignore，`config.mts` 中同步读取、文件不存在时静默跳过：

```ts
const LAB_CONFIG = resolve(dirname(fileURLToPath(import.meta.url)), 'lab.local.json')
const lab = isDev && existsSync(LAB_CONFIG)
  ? JSON.parse(readFileSync(LAB_CONFIG, 'utf-8')) : {}
```

**容错是必需的**——clone 下来的仓库没有这个文件，构建不能因此失败。

`images/` 同样在 `.gitignore` 中——原始物料的本地备份。

## 写作时的自我审查

公开意味着**写进去就撤不回**：页面可以删，GitHub 提交历史删不掉。因此以下内容不写入：

| 不写 | 原因 |
|---|---|
| 客户明确要求保密的信息 | 保密义务 |
| 未公开的价格条款、合同细节 | 商业敏感 |
| 第三方提供的未授权素材 | 版权 |
| 拿不准的 | **拿不准就是不写的理由** |

`docs/lab/index.md` 顶部有对应的警示块。

## 项目推进节奏

阶段之间**串行**，每个阶段有明确产出与放行条件：

| 阶段 | 产出 | 放行条件 |
|---|---|---|
| 0 · 立项 | `00-brief.md` | 已知与未知划分清楚，风险项列出 |
| 1 · 提案 | `01-proposal.md` `02-materials.md` | 内部讨论通过 |
| 2 · 对客 | 客户反馈写回 `00-brief.md` | 方向确认、物料到位 |
| 3 · 分镜 | `03-storyboard.md` | 逐镜标注可生成性 |
| 4 · Prompt | `04-prompts.md` | 按工具分组，不可生成的镜头标出替代方案 |
| 5 · 生成 | `05-genlog.md` | 全片跑通一版再抠单镜 |
| 6 · 后期交付 | 成片 | —— |
| 7 · 复盘 | `06-review.md` | 交付后立即写 |

**关键约束：阶段 1 未放行，不写分镜和 Prompt。** 提案方向一变，分镜全废——这是最容易发生的浪费。

## 与既有教学案例的关系

知识库中已有与首个真实项目**同题材的教学演示案例**。它的方法论骨架可以复用，但产品设定为纸上推演，与真实产品在包装形态、卖点、口味上均不同。

处理方式：在 `00-brief.md` 中单列一节，逐条记录**推演的哪些假设被真实产品推翻了**。

这是这个板块未来最有价值的产出之一——「纸上推演 vs 真实项目的差距」，只有同时握有两者的人写得出来。

## 验收标准

- `npm run docs:build` 零错误、零死链，`lab/` 下页面全部生成。
- 导航与侧边栏可达作战区，产品图正常打包。
- 对客文件（`01-proposal.md`、`02-materials.md`）不含任何站内链接，可整份复制发送。

## 决策变更记录

### 原方案：三层隔离（已实现并验证，随后移除）

| 层 | 机制 |
|---|---|
| dev 可见 | `const isDev = process.argv.includes('dev')`，nav/sidebar 条件注入 |
| build 排除 | `srcExclude: isDev ? [] : ['lab/**']` |
| git 排除 | `.gitignore` 中的 `docs/lab/` |

判断 `process.argv` 而非 `NODE_ENV`，因为 `vitepress preview` 跑的是构建产物，行为必须与 build 一致。

验证通过：产物中无 lab 路径、无客户名，`git status` 不含工作区文件。

### 中间讨论：隐藏链接与前端密码

变更过程中评估过两个折中方案，结论如下，**留档以免日后重复讨论**：

| 方案 | 结论 |
|---|---|
| 页面不进导航，只能靠 URL 访问 | **不构成保护。** 构建产物推送到公开的 `pages` 分支，任何人可直接浏览到 HTML 文件，无需知道站点 URL |
| 前端密码（明文比对后显示） | **等同无保护。** 密码与内容均在客户端 JS 中 |
| 整页 AES 加密（StatiCrypt 类） | 有效，但密文公开挂网可被离线暴力破解，且密码一经转发即永久失效 |
| Cloudflare Pages + Access | **唯一的服务端鉴权方案**，未认证者拿不到任何字节，免费额度可用，且支持私有仓库 |

GitHub Pages 自带的访问控制仅 Enterprise 版提供，Pro 不含——该路线在当前部署方式下不可行。

### 中途决定：直接公开（2026-08-05，次日推翻）

隔离机制全部移除。当时列出的已知代价：

- **不可撤销**——页面可删，GitHub 提交历史不可删
- 客户名、产品渲染图、工期与报价框架、内部决议均公开
- 首个项目的产品渲染图**商用授权尚未确认**，该风险独立于本决策存在，已列入物料清单

### 最终决定：恢复三层隔离（2026-08-06）

**推翻公开决定的，正是它自己列出的第三条代价——只不过触发它的是另一个条件。**

2026-08-06 向客户确认后得知：**首个项目的产品尚未上市，属新品待发。**

而该项目的物料清单里，我方自己写过一条处置规则：

> 若产品未上市，包装图与工艺资料按机密处理。

**这条规则成立了，但没有执行。** 板块仍是公开的，客户名、产品名与规格、包装渲染图、提案与工期框架已推送至公开仓库并部署上线。

::: danger 这次失误的性质
不是没想到，是**想到了、写下来了、条件成立了，然后没人去执行**。

物料清单第 11 项当时写的是「产品是否已上市 / 预计上市时间」，归在 🟢「影响判断」组——**它被当成了一个影响创意判断的问题，而不是一个触发保密动作的开关。**

分类决定了它被怎么对待。一个会触发处置动作的条件，不该和「目标人群」「审批轮次」放在同一组。
:::

处置：

| 动作 | 说明 |
|---|---|
| 恢复三层隔离 | 见上文「可见性」，并补上第一次遗漏的导航配置隔离 |
| 重写 `main` 历史 | 前三个 commit 不含作战区，从引入点软回退后重做，历史损失最小 |
| 重建 `pages` 分支 | 真正在线可访问的是构建产物分支，**只处理 main 不解决问题** |
| 本地保留全部工作产物 | 移出版本控制，不删文件 |

### 关于「重写历史」能做到什么

需要如实记录，以免日后误以为这类操作等于抹除：

| 能做到 | 做不到 |
|---|---|
| 移除仓库默认可见路径 | 抹除托管方可能缓存的旧对象——知道 commit SHA 仍可能访问一段时间 |
| 下线站点上的页面与图片 | 收回已被搜索引擎、归档站或他人抓取的内容 |
| 阻止后续继续泄露 | 撤回已经发生的暴露 |

**force push 是止损，不是撤销。** 唯一真正有效的是一开始就不要公开——这次的教训成本已经付了。

### 由此产生的一条通用约束

**涉及真实客户的工作区，默认不公开。** 要公开的是脱敏之后、项目交付之后的复盘，写进 `cases/`。

「边做边写」的价值来自记录的即时性，不来自公开的即时性。**这两件事可以分开，而且必须分开。**
