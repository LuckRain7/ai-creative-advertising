Codex + Gemini Flow：广告视频生产流水线 ​

一条半自动的短视频生产链路：Codex 客户端在本地做编排与文件管理，Gemini Flow 在浏览器里做实际生成，两者靠文件和剪贴板交接。

工具形态变动极快

Codex 与 Flow 的功能边界、订阅档位、模型版本都在快速迭代。本篇只写链路结构与分工逻辑——这部分稳定。具体某个按钮在哪、某个模型能生成多长，以官网和你自己的实测为准。

这条链路解决什么问题 ​

一支 12 镜头的广告片，实际工作量不在"生成"，而在生成前后的两堆杂活：

环节手工做的样子占用时间
生成前12 条 prompt 一条条敲，风格段反复复制粘贴，改一次全改大
生成中在网页里贴、等、下载中
生成后下载文件夹里 40 个 video_final(3).mp4，人肉认哪个是哪个镜头最大

**Codex 的价值在头尾两段，Flow 的价值在中间那段。**这条链路的全部设计，都是为了让两边各自只干自己擅长的事。

为什么是这个组合 ​

Codex 客户端Gemini Flow
位置本地浏览器
强在文件读写、跑命令、长任务、多 agent 并行Veo 生成、原生同步音频、图像（Nano Banana）
弱在自己不产画面没有本地文件系统，管不了你的素材归档
角色车间主任摄影棚

Flow 的一个结构性优势

Veo 系列原生生成同步音频——环境音、对白、音乐与口型是单次输出的一部分，不是后期配上去的。

对广告来说这一条很重要：它意味着 片型图谱 里「感官片音效要单独设计」的工作量，有一部分可以前移到生成阶段。但成品是否达到交付水平仍需实测，见文末「对既有判断的影响」。

交接界面：这条链路的命脉 ​

两个系统之间没有 API，只有文件。所以命名规范不是整洁问题，是能不能自动化的问题。

project/
├── AGENTS.md            # Codex 的项目说明书
├── brief.md             # 原始需求
├── shots.md             # 分镜表（Codex 产出，人审）
├── prompts/
│   ├── style-block.txt  # 固定风格段，所有镜头共用
│   └── shot-01.txt ...  # 每镜一个 prompt 文件
├── inbox/               # 浏览器下载目录的软链或同步目录
├── clips/
│   ├── shot-01_v1.mp4
│   └── shot-01_v2.mp4   # 同镜头多版本，靠 _v 后缀区分
├── qc.md                # 质检台账
└── out/

唯一不能省的规矩

从 Flow 下载的文件，落地后立刻改名。

不改名，inbox/ 三十分钟后就变成一堆 Flow_video(7).mp4，这条链路的自动化部分全部失效——因为 Codex 也认不出哪个是哪个镜头。

这一步可以交给 Codex 做（见下半部分），但不能不做。

上半部分 · Codex 当编排 agent ​

这一段不需要写代码，创意岗可以直接照做。把 Codex 客户端当成一个能读写你项目文件夹的助理。

阶段一：拆 brief，产出分镜表 ​

你给它：brief.md（客户原话就行）+ 已经定好的片型和 Big Idea。

不要让它从零想创意

片型和 Big Idea 应该在进入这条链路之前就定好。理由见 Big Idea 与洞察——AI 负责穷举，人负责判断。

这条流水线是执行流水线，不是创意流水线。拿它做创意，你会得到一支结构工整但没人在意的片子。

让它做：把创意拆成镜头序列，输出到 shots.md。

给 Codex 的指令大致长这样：

读 brief.md 和 shots-spec.md。

把这条创意拆成 10–14 个镜头，输出 shots.md，每镜一行表格：
镜号 | 时长(秒) | 景别 | 画面内容 | 声音内容 | 在结构里的作用

约束：
- 总时长 [30] 秒，竖屏 9:16
- 第 1 镜必须在 1.5 秒内出钩子
- 每镜只有一个运镜，不要复合运镜
- 标出哪些镜头是产品特写（这些不能有人物）

它产出：一张分镜表。你要做：审一遍，砍掉废镜头。镜头语言的标准词表见 分镜设计。

阶段二：批量产 prompt，风格段固化 ​

这是 Codex 相对手工优势最大的一步。

核心做法：把 Prompt 结构通法 的五段式拆成两半——

部分内容是否变化
风格段色调、光线、镜头质感、胶片感、画幅全片固定，一个字都不改
主体段这一镜的主体、动作、运镜每镜不同

指令：

读 shots.md 和 prompts/style-block.txt。

为每个镜头生成一个 prompt 文件 prompts/shot-NN.txt：
- 开头原样引用 style-block.txt 的全部内容
- 之后接这一镜的主体、动作、运镜描述
- 每条必须完整自描述——假设生成模型完全不知道前后镜头，
  场景、人物、氛围一律从头写全，禁止出现「同上一镜」这类引用
- 有声音需求的，在末尾用单独一段描述环境音与对白

一次只处理 5 个镜头，做完停下来等我确认，再继续下一批。
不要自作主张修改 style-block 的任何措辞。

「一次 5 条」不是随手定的

Kalshi 案例的创作者明确提到：让模型一次生成超过 5 条 prompt，质量会开始下滑。

这一条经验值得照搬。批量生产的诱惑是「一次把 12 条全出了」，但生成 12 条平庸的 prompt，不如分 3 批出 12 条能用的——返工成本在后面等着你。

来源见 案例 06 · Kalshi NBA 决赛 AI 广告。

「完整自描述」这条同理：模型没有跨条目的上下文记忆，你以为的「承接上一镜」，它读不到。信息冗余优于引用——这也是为什么风格段要原样拼接到每一条，而不是写一句「风格同前」。

为什么这一步值回票价

风格漂移是 AI 素材最常见的翻车原因（见 品牌一致性控制）。手工复制风格段，12 次里总会有一两次漏字或改词，而这种偏差在成片里看得出来。

更重要的是改的时候：客户说"整体再暖一点"，你只改 style-block.txt 一个文件，让 Codex 重新生成 12 条。手工做这件事要 20 分钟且容易漏。

阶段三：人在 Flow 里生成 ​

这一段目前仍然是手工的（进阶做法见下半部分的 computer use 一节）。

做法说明
优先走图生视频先用 Nano Banana 出满意的首帧，再驱动。可控性远高于文生视频，理由见 工具全景对照表
一次只测一镜先跑通第 1 镜确认风格对，再批量跑其余的。风格错了批量跑等于批量废
每镜多生成几版废片率高是常态，不是失败。当场别细挑，先都下载
下载后立刻改名见上面的规矩

阶段四：Codex 接管归档与质检 ​

指令：

把 inbox/ 里的新文件按我说的镜号改名成 clips/shot-NN_vM.mp4，
读取每条的时长和分辨率，更新 qc.md 表格。
时长不足 shots.md 要求的，在表里标红。

它产出：一张台账，告诉你哪些镜头还没有合格素材。

这一步是整条链路里最省时间的

40 个文件的认领、改名、登记，手工要半小时且极易出错。这是纯机械劳动，交出去毫无损失。

下半部分 · Codex 当生产引擎 ​

这一段偏技术。不写代码的话，读一眼小标题知道"这些事能自动化"就够了。

AGENTS.md：让 Codex 记住项目规矩 ​

在项目根目录放一份 AGENTS.md，Codex 会自动读它，省掉每次重复交代：

markdown
# 项目：[品牌] 30 秒竖屏广告

## 目录约定
- prompts/  每镜一个 txt，风格段来自 style-block.txt，禁止修改
- inbox/    浏览器下载目录，文件一律视为待归档
- clips/    命名 shot-NN_vM.mp4，NN 两位镜号，M 版本号
- out/      成片，不要手动放东西进来

## 交付规格
- 9:16，1080×1920，H.264
- 总时长 30 秒 ±0.5 秒
- 字幕安全区：上下各留 15%

## 硬规矩
- 不要修改 style-block.txt，除非我明确要求
- 不要删除 clips/ 里的任何文件，废片只在 qc.md 里标记
- ffmpeg 命令先打印出来给我看，确认后再执行

最后一条不要省

ffmpeg 用错参数会静默地产出一个能播但规格错误的文件——码率不对、色彩空间偏移、音轨丢失。这类错误在预览时看不出来，交付后才被发现。

让它先打印命令，比事后返工便宜得多。

批次改名 ​

从浏览器下载的文件名不可控。让 Codex 生成一次性脚本处理：

bash
# 按修改时间排序，批量归档到指定镜号
ls -t inbox/*.mp4 | tail -r | awk -v n=1 '{
  printf "mv \"%s\" clips/shot-%02d_v1.mp4\n", $0, n++
}'

先打印、确认顺序对，再 | sh 执行。

拼接与规格统一 ​

素材齐了之后，成片阶段的三件事：

bash
# 1. 生成拼接清单
printf "file '%s'\n" clips/shot-*_final.mp4 > out/list.txt

# 2. 拼接（统一重编码，不用 -c copy——AI 素材的编码参数往往不一致）
ffmpeg -f concat -safe 0 -i out/list.txt \
  -vf "scale=1080:1920:force_original_aspect_ratio=increase,crop=1080:1920,fps=30" \
  -c:v libx264 -preset slow -crf 18 -pix_fmt yuv420p \
  -c:a aac -b:a 192k out/cut.mp4

# 3. 全片套同一个 LUT，统一色调
ffmpeg -i out/cut.mp4 -vf "lut3d=look.cube" \
  -c:v libx264 -crf 18 -c:a copy out/final.mp4

第 3 步是 AI 素材的救命稻草

每个镜头的色温都不太一样，这是生成模型的固有问题。全片套同一个 LUT，能救回相当一部分风格漂移，性价比远高于回去重新生成。

这一条在 工具全景对照表 里也提过，值得再说一遍。

质检台账 ​

让 Codex 维护 qc.md，每一版素材一行：

镜号版本时长手部文字产品保真色温结论
01v13.2s✓✓✗ logo 变形偏冷废
01v23.0s✓✓✓✓采用

前四项 Codex 判断不了，要人看。但时长、分辨率、码率它能自己读，而这几项恰恰是最容易被忽略、最容易在交付时爆炸的。

进阶：用 computer use 直接驱动 Flow ​

Codex 客户端具备 computer use 与内置浏览器，理论上可以自己打开 Flow、贴 prompt、等待、下载——把上半部分的阶段三也自动化掉。

这条路我建议先别走

三个理由：

  1. 可靠性。网页 UI 会改版，视觉驱动的自动化非常脆。跑通一次不代表下周还能跑。
  2. 筛选无法外包。生成结果好不好必须人看。自动化了"贴和下载"，但没自动化"判断"——而后者才是瓶颈。
  3. 账号风险。用自动化方式操作订阅制服务，可能触碰服务条款。下单前自己确认清楚。

**真正值得自动化的是搬运，不是判断。**目前人工贴 prompt 的成本，远低于维护一套脆弱自动化的成本。

这条链路的边界 ​

诚实地划出来：

它擅长它不擅长
镜头多、风格统一要求高的片子单镜头的一次性素材（杀鸡用牛刀）
需要反复改版重跑的项目一次成型不再改的项目
产品、空镜、场景类画面真人表演类（见下）
你愿意维护目录规范想随手做完就走

建流水线本身有成本

第一次搭这套目录和 AGENTS.md，大概要花掉一个下午。这个投入在第二个项目才回本。

只做一支片子，手工更快。

对既有判断的影响 ​

待实测

Veo 系列原生生成同步音频，包括对白与口型。这与 片型图谱 里的判断存在张力——那一页给「代言人口播 / 达人测评」打了 ★☆☆☆☆，理由正是口型同步和表演自然度。

**这一条需要实测后回来更新。**要验证的是三件事：

  1. 口型同步能否达到广告交付水平（不是"能看"，是"客户不会指出来"）
  2. 中文对白的效果是否与英文一致
  3. 微表情和肢体动作的自然度是否同步改善——口型对上了但表情僵硬，依然出戏

在实测结论出来之前，片型图谱 的星级判断不动。新功能发布 ≠ 能交付，这两者之间通常隔着好几个版本。

另外，人物肖像与声音的授权红线不受技术进步影响，见 人物代言。
